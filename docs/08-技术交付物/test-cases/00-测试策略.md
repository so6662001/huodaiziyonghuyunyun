# 货袋子平台测试策略

## 一、测试金字塔

```
          ┌─────────────┐
          │   E2E       │  10%  关键业务闭环（用户→平台→交易）
          ├─────────────┤
          │ 集成测试    │  20%  API 间、服务间集成
          ├─────────────┤
          │ 单元测试    │  70%  函数/组件/算法
          └─────────────┘
```

## 二、测试范围

### 1. 测试类型

| 类型 | 目标覆盖率 | 工具建议 |
|---|---|---|
| 单元测试 | 后端 ≥ 80% / 前端 ≥ 60% | Jest, JUnit, Pytest, Go testing |
| 集成测试 | 关键接口 100% | Postman, REST Assured, Pact |
| E2E 测试 | 关键业务流 100% | Playwright, Cypress |
| 性能测试 | 核心接口 + 派单 + AI | JMeter, k6, Locust |
| 安全测试 | 全部 API + 数据传输 | OWASP ZAP, Burp Suite |
| 兼容性测试 | 主流浏览器 + 微信 + iOS/Android | BrowserStack |
| 灰度验证 | 每次发版 | 内部用户先行 |

### 2. 覆盖范围

- ✅ M1-M11 全部 11 模块
- ✅ 63 个 API 端点
- ✅ 33 张数据库表
- ✅ 36 条风控规则
- ✅ 关键业务流（发需求→撮合→成交，清单上传→拆单→选方案）

## 三、测试用例分级

| 等级 | 标准 | 占比 |
|---|---|---|
| P0 致命 | 阻塞核心业务 | 20% |
| P1 重要 | 影响主要功能 | 50% |
| P2 一般 | 边界 case | 25% |

## 六、测试环境

### 1. 环境清单

| 环境 | 用途 | 数据 |
|---|---|---|
| dev | 开发自测 | 真实结构 + 假数据 |
| test | QA 测试 | 完整测试数据集 |
| staging | 灰度发布 | 部分真实流量 |
| prod | 生产 | 真实数据 |

### 2. 测试数据管理

- `02-initial-data.sql` 提供初始测试数据
- 每次跑用例前重置数据库（或事务回滚）
- 敏感数据（手机号、身份证）使用 fake 数据
- AI 服务用 Mock（不消耗真实额度）

## 七、CI/CD 集成

```
PR 提交
  ↓
单元测试（必须通过）
  ↓
代码 review
  ↓
合并到 dev
  ↓
集成测试 + 部分 E2E（必须通过）
  ↓
部署到 test
  ↓
全量 E2E + 性能基线（必须通过）
  ↓
部署到 staging（灰度）
  ↓
监控 24h + 关键指标
  ↓
全网上线
```

## 八、关键测试指标

| 指标 | 目标 |
|---|---|
| 代码覆盖率（核心模块） | ≥ 80% |
| 用例通过率 | ≥ 98% |
| 缺陷逃逸率（生产环境） | < 5% |
| 严重缺陷修复时间 | < 24h |
| 回归测试自动化率 | ≥ 70% |

## 九、缺陷分级与处理

| 等级 | 定义 | 修复时间 |
|---|---|---|
| Critical | 阻塞核心业务、数据丢失、安全漏洞 | 立即 |
| High | 主要功能不可用 | 24h |
| Medium | 次要功能问题或体验问题 | 1 周 |
| Low | 优化建议 | 下个迭代 |

## 十、灰度验证 SOP

1. **Day 0**：内部 30 人验证
2. **Day 1-2**：唐山 100 卖家 + 50 买家
3. **Day 3-7**：唐山+天津 500 卖家 + 200 买家
4. **Day 7-14**：全网放开

任一阶段出现 Critical → 立即回滚 + 复盘。

## 十一、应急测试场景（演练）

定期演练以下应急场景：

- 数据库主从切换
- 缓存全挂
- AI 服务超时
- 第三方支付故障
- 微信 API 异常
- 大流量突发（DDoS / 营销活动）

每季度至少 1 次完整演练。
