# 应急响应 SOP

## 一、故障分级

| 等级 | 定义 | 响应时间 | 通知 |
|---|---|---|---|
| **P0 致命** | 全站不可用 / 数据丢失 / 安全事件 | 5 分钟内 ack | CEO + CTO + 全员 |
| **P1 严重** | 核心功能不可用（如下单/登录） | 15 分钟内 ack | CTO + 相关 VP |
| **P2 一般** | 次要功能或体验问题 | 1h 内 ack | 相关团队 |
| **P3 轻度** | 不影响业务，建议改进 | 1 工作日 | 邮件 |

## 二、P0 故障处理流程

```
T+0       告警 / 用户反馈
            ↓
T+1min    SRE on-call ack 告警
            ↓
T+3min    SRE 初步判断 → 拉群（CTO + 相关）
            ↓
T+5min    群内宣布"故障作战开始"
            ↓
T+10min   定位 + 决策恢复方案
            ↓
T+15min   执行恢复（回滚 / 切流 / 重启）
            ↓
T+30min   服务初步恢复
            ↓
T+1h      全量恢复 + 验证
            ↓
T+2h      对外公告（如需要）
            ↓
T+24h     发布完整事后分析报告
            ↓
T+1w      改进措施落地 verification
```

## 三、关键角色与职责

```
故障指挥官（Incident Commander）：
  - 通常是 CTO 或值班 SRE 负责人
  - 全权决策
  - 协调资源

技术负责人（Tech Lead）：
  - 定位根因
  - 决定恢复方案

沟通负责人（Communications）：
  - 群内同步
  - 对外公告
  - 客服话术

记录员（Scribe）：
  - 时间线记录
  - 事后报告
```

## 四、应急通讯

### 1. 主战群（钉钉/企微）

```
"货袋子-紧急故障作战群"
  - 永久存在
  - 7×24h 监听
  - 仅用于 P0/P1 故障
  - 必须有 CEO + CTO + 关键人员
```

### 2. 备用通讯

```
如主群不可用（如钉钉故障）：
  备用 1：企微"应急联络"群
  备用 2：电话联系链
  备用 3：邮件
  备用 4：物理见面（极端情况）
```

### 3. 对外公告

```
故障 30 分钟内仍未恢复 → 在以下渠道公告：

- 平台首页公告横幅
- 微信小程序通知
- 微信群通知（2000 群）
- 客服话术更新

公告内容：
  - 影响范围
  - 预计恢复时间
  - 解决方案
  - 道歉

不公布：
  - 技术细节（避免被利用）
  - 具体根因（事后再说）
```

## 五、典型故障预案

### 预案 1：数据库主库宕机

```
症状：
  - 大量 500 错误
  - 数据库连接失败告警

应对：
  1. 立即从库提升为主库
  2. 应用配置切换
  3. 监控数据一致性

预计恢复：15-30 分钟
```

### 预案 2：Redis 缓存全挂

```
症状：
  - 数据库连接数飙升
  - 查询接口延迟激增

应对：
  1. 启用降级（部分接口直接返回）
  2. 限流（保护数据库）
  3. 重建 Redis 集群
  4. 缓存预热

预计恢复：30-60 分钟
```

### 预案 3：第三方 AI 服务超时

```
症状：
  - AI 识变接口大量超时
  - 清单解析失败

应对：
  1. 切换备用厂商（如：通义千问 → GPT）
  2. 启用规则引擎降级
  3. 提示用户"AI 暂时不可用，请手动操作"

预计恢复：5-15 分钟
```

### 预案 4：DDoS 攻击

```
症状：
  - 流量异常激增
  - 大量来自单一区域/IP

应对：
  1. 启用 WAF 紧急规则
  2. 限流 + 验证码
  3. 联系云厂商高防
  4. 异常 IP 拉黑

预计恢复：取决于攻击规模
```

### 预案 5：第三方支付故障

```
症状：
  - 充值失败率激增

应对：
  1. 切换支付通道（微信 → 支付宝）
  2. 给用户重试提示
  3. 联系支付商客服

预计恢复：30-60 分钟
```

### 预案 6：微信开放平台异常

```
症状：
  - 微信登录失败
  - 企微机器人无响应

应对：
  1. 提示用户用手机号登录
  2. 关闭企微机器人推送
  3. 等待微信恢复

预计恢复：取决于微信
```

### 预案 7：数据泄露

```
症状：
  - 异常数据导出
  - 黑客索取赎金

应对：
  1. 立即隔离受影响系统
  2. 通知 CEO + 法务 + 公安
  3. 取证（不要清理日志）
  4. 评估影响范围
  5. 通知受影响用户
  6. 整改

注意：
  - 必须在 72h 内向监管机构报告（数据安全法）
  - 必须向受影响用户告知
```

### 预案 8：卖家集体抵制

```
症状：
  - 区域响应率突降 > 20%
  - 商会负面舆情
  - 大量退会员申请

应对：
  1. 启动卖家委员会临时会议
  2. CEO 亲自走访关键卖家
  3. 暂停引发反弹的规则
  4. 出整改方案 + 公开道歉
  5. 必要时退还会员费

参考：docs/04-战略迭代/04-1-反卖家反弹方案.md
```

## 六、事后分析报告（Postmortem）

### 模板

```markdown
# 故障复盘报告 - YYYY-MM-DD

## 1. 摘要

- 故障级别：P0
- 故障开始：2026-05-23 14:32
- 故障结束：2026-05-23 15:18
- 总时长：46 分钟
- 影响：约 5000 用户无法登录

## 2. 时间线

| 时间 | 事件 |
|---|---|
| 14:32 | 监控告警：登录接口错误率飙升 |
| 14:33 | SRE @张三 ack 告警 |
| 14:35 | 定位：Redis Sentinel 故障 |
| 14:40 | 决策：重启 Sentinel + 切流 |
| 14:55 | Sentinel 恢复，登录恢复 |
| 15:18 | 全量验证通过 |

## 3. 根因分析

直接原因：Sentinel 主节点 OOM
深层原因：监控指标缺失 + 自动重启策略未配置
触发条件：流量突增

## 4. 影响评估

- 用户：5000 登录失败
- 业务：约 ¥50000 GMV 流失
- 品牌：部分用户反馈

## 5. 经验教训

✅ 做得好的：
  - 5 分钟内 ack
  - 决策果断

❌ 做得不好的：
  - 缺监控
  - 缺自动重启

## 6. 改进措施

| 措施 | Owner | 截止日 | 状态 |
|---|---|---|---|
| 加 Sentinel 监控 | 张三 | 5/30 | 待办 |
| 配置自动重启 | 李四 | 5/30 | 待办 |
| 容量评估 | 王五 | 6/15 | 待办 |

## 7. 不追责承诺

本次复盘聚焦改进，不追责个人。
```

### 复盘原则

```
1. 对事不对人（Blameless Postmortem）
2. 24h 内完成
3. 全员可见
4. 所有改进措施必须有 Owner + 截止日
5. 每月跟踪改进措施落地情况
```

## 七、故障演练（混沌工程）

```
工具：Chaos Mesh / Chaos Monkey

定期演练：
  - 每周自动注入小故障（如：单 Pod kill）
  - 每月人工注入中等故障（如：单服务down）
  - 每季度全员演练大故障（如：数据库宕机）

目的：
  - 验证应急流程
  - 训练团队
  - 暴露系统弱点
```

## 八、客服话术

### 用户问"为什么用不了？"

```
"非常抱歉，平台目前正在紧急处理一个技术问题，
预计 [时间] 内恢复。给您带来的不便我们深表歉意。
后续我们会发布详细说明并改进。

需要紧急处理的业务请联系：[紧急联系电话]"
```

### 不要说

- ❌ "服务器爆了" / "工程师在加班"
- ❌ "应该一会就好"（要给具体时间）
- ❌ 透露技术细节
- ❌ 推卸责任
