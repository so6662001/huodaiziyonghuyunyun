# 11 - AI 开发工作流 SOP

> **用途**：把 AI 编程从"碰运气"变成"工业化生产"。
> **本质**：标准化"输入 → 处理 → 输出 → 验证"四个环节。

---

## 二、每个阶段的具体话术

### 阶段 1：需求理解

#### 1.1 发送给 AI 的 Prompt

```
[已开启 .cursorrules / 已贴 00-核心系统提示词]

任务：实现 [功能名]

PRD：docs/07-产品PRD-v2/02-采购会话核心模块.md（第 2.3 节）

请在编码前，先完成"需求理解"任务：

1. 通读 PRD 第 2.3 节，列出所有功能点（功能 1、功能 2、...）
2. 扫描动词（创建/修改/删除/通知/...），列出所有动作
3. 扫描数字（最大/最小/上限），列出所有规则
4. 扫描"如果"，列出所有边界
5. 列出涉及的数据库表（去 DDL 找）
6. 列出涉及的 API（去 openapi.yaml 找）
7. 列出涉及的既有代码（去 backend/ 找）
8. 列出潜在风险点

输出格式：
## 功能点清单
1. ...
2. ...

## 边界情况清单
1. ...
2. ...

## 涉及资源
- 表：xxx, yyy
- API：POST /api/v1/xxx
- 文件：backend/xxx-service/xxx.java

## 风险
1. ...

请不要立即写代码。
```

#### 1.2 人工审核要点

```
□ 功能点清单是否对照 PRD 完整？
□ 边界情况是否充分？（至少 5 个）
□ 涉及资源是否准确？（去查证）
□ 风险点是否合理？

如果有遗漏，回复 AI：
  "你漏了 PRD 中提到的 xxx，请补充"
  → 让 AI 重新输出
```

### 阶段 2：方案设计

#### 2.1 发送给 AI 的 Prompt

```
[需求理解已确认]

现在请输出技术方案：

1. 数据流图（用 Mermaid 画出）
2. 状态机图（如适用）
3. 关键 API 调用顺序
4. 数据库变更（如需新增字段）
5. 错误处理策略
6. 性能优化策略（缓存？异步？批量？）
7. 安全考量
8. 监控埋点
9. 与其他模块的交互
10. 关键决策点（A vs B 方案对比）

输出格式：

## 1. 数据流
```mermaid
sequenceDiagram
  ...
```

## 2. 状态机
```mermaid
stateDiagram-v2
  ...
```

## 3. API 调用顺序
...

## 4. 数据库
...

(其他)

## 关键决策

### 决策 1：xxx
- 方案 A：...（优点/缺点）
- 方案 B：...（优点/缺点）
- 推荐：方案 A，理由：...
```

#### 2.2 人工审核要点

```
□ 数据流是否合理？
□ 状态机是否完备？（每个状态都有出路）
□ 错误处理是否充分？
□ 性能优化是否过度（不要 over-engineering）
□ 关键决策是否合理？

如果不通过，明确告诉 AI 改哪里。
```

### 阶段 3：实现

#### 3.1 发送给 AI 的 Prompt

```
[技术方案已确认]

现在请按方案实现代码。

要求：
1. 按以下顺序实现：
   - DB 变更（如需）
   - Entity
   - Mapper
   - DTO（Request + Response）
   - Converter（MapStruct）
   - Service 接口
   - ServiceImpl
   - Controller
   - 单元测试
   - 集成测试

2. 每个文件给完整代码（不要省略 ...）

3. 给出文件的完整路径

4. 解释关键设计

5. 同步更新：
   - openapi.yaml（如新增 API）
   - 错误码表（如新增错误码）

请开始。
```

#### 3.2 实现完成后让 AI 输出报告

```
实现完成。请输出实现报告：

## 文件清单

新增：
- backend/xxx-service/src/main/java/.../XxxController.java
- ...

修改：
- ...

## 关键设计

1. ...
2. ...

## 测试结果

```
$ mvn test
...
Tests run: 15, Failures: 0
BUILD SUCCESS
```

## 已知问题 / Trade-off

1. ...

## 下一步建议

1. ...
```

### 阶段 4：AI 自评

#### 4.1 发送给 AI 的 Prompt

```
现在请切换到「严格 Code Reviewer」角色。

不要客气，不要找借口，挑出问题。

请按【docs/14-AI开发提示词/06-代码评审提示词.md】的 10 个维度评审，
并按【docs/14-AI开发提示词/10-验收checklist.md】的 100 项打勾。

如果发现问题，立即修复后再次评审，直到所有项目通过。

最终输出格式：

## Code Review 报告（第 X 轮）

### 严重问题（已修复）
- ...

### 一般问题（已修复 / 决定不修）
- ...

### 验收 Checklist
- 需求一致性：8/8 ✓
- API 契约：11/11 ✓
- 数据库：10/10 ✓
- ...
- 总分：97/100

### 决策：✅ 可合并 / ❌ 不可合并

### 不能合并的原因（如有）
...
```

#### 4.2 人工抽查

```
不要全信 AI 自评。抽查：
- 随机选 1 个文件，全文精读
- 检查 AI 自评是否如实（有没有漏掉问题）
- 测试关键场景
- 查看 PR diff，确认没多余改动
```

### 阶段 5：人工评审

#### 5.1 评审 SOP

```
1. 看 PR 描述
   □ 改动目的清晰？
   □ 关联了 PRD / Issue？
   □ 包含自检 checklist？

2. 看 CI/CD
   □ 编译通过？
   □ 测试通过？
   □ 静态分析通过？

3. 看 AI 自评报告
   □ 报告完整？
   □ 没有避重就轻？

4. 抽查代码
   □ 选 2-3 个核心文件精读
   □ 选 1 个测试验证测试质量
   □ 检查与 PRD 的一致性

5. 测试关键场景
   □ 本地拉分支
   □ 跑核心流程
   □ 尝试边界情况

6. 给意见
   □ 必改项（Blockers）
   □ 建议项（Nice-to-have）
   □ 表扬亮点
```

#### 5.2 评审耗时建议

```
小 PR（< 200 行）：15 分钟
中 PR（200-500 行）：30-45 分钟
大 PR（500-1000 行）：60-90 分钟
超大 PR（> 1000 行）：拒绝评审，要求拆分

平均每个 PR 评审耗时应控制在 30 分钟以内（依赖 AI 自评质量）。
```

## 三、不同场景的工作流

### 场景 1：新增功能（标准流程）

按上面的 6 阶段走。

### 场景 2：修 Bug

```
阶段 1：根因分析（用【07-Bug 修复提示词】）
阶段 2：修复方案
阶段 3：实现 + 回归测试
阶段 4：AI 自评
阶段 5：人工评审
阶段 6：合并
```

### 场景 3：UI 还原

```
阶段 1：阅读 HTML 原型 + 设计规范（用【03-UI 高保真还原提示词】）
阶段 2：列出 design token + 组件
阶段 3：实现（同时输出标注表）
阶段 4：自查 token 一致性
阶段 5：与原型对比（截图）
阶段 6：合并
```

### 场景 4：写测试

```
阶段 1：列出测试场景（正常 + 异常 + 边界）
阶段 2：选择测试类型（单元 / 集成 / E2E）
阶段 3：实现测试
阶段 4：跑测试 + 检查覆盖率
阶段 5：合并
```

### 场景 5：紧急 Hotfix

```
跳过部分阶段，但绝不跳过：
□ 阶段 1 根因分析（5 分钟）
□ 阶段 3 实现 + 回归测试（必须）
□ 阶段 4 AI 自评（必须）
□ 阶段 5 人工抽查（必须，至少 1 人）

不允许跳过：测试、Code Review

允许跳过：完整 Checklist、性能测试、E2E
```

## 五、效率指标

```
理想的 AI 开发效率：

| 任务规模 | 传统开发 | AI 辅助 | 提升 |
|---|---|---|---|
| 简单 CRUD（1 个接口） | 0.5 天 | 1-2 小时 | 3x |
| 中等功能（5 个接口 + UI） | 3-5 天 | 1-2 天 | 2.5x |
| 复杂功能（完整模块） | 2-3 周 | 4-7 天 | 3x |

如果你 AI 辅助开发还不到 1.5x 提速，说明：
1. 提示词没用好
2. AI 自评没做好
3. 在 AI 翻车上耗了太多时间

→ 回到阶段 1，加强需求理解
```

## 六、团队协作

### 6.1 角色分工

```
PM：
- 写 PRD（必须详细，不留模糊空间）
- 提供 PRD 给 AI

架构师：
- 评审 AI 的技术方案
- 制定 / 维护本目录的提示词

工程师：
- 与 AI 协作开发
- 人工抽查 + 评审

QA：
- 写测试用例
- 让 AI 自动化执行测试

设计师：
- 提供 Figma / HTML 原型
- 审核 AI 的 UI 还原
```

### 6.2 知识沉淀

```
每周一次"AI 翻车回顾"：
  - 收集本周 AI 失败的 case
  - 分析根因
  - 更新提示词
  - 在团队周会分享

每月一次"提示词演进":
  - 评估各提示词的有效性
  - 删除冗余
  - 补充新场景
  - 版本号 +1
```

## 七、常见反模式

```
❌ 反模式 1："让 AI 一把梭"
  「AI 帮我实现 xx 功能」→ AI 直接写代码
  问题：没有需求理解阶段，必漏功能
  正解：必须分阶段，先列功能点

❌ 反模式 2：盲信 AI
  AI 说："代码完美无瑕"
  问题：AI 经常自我感觉良好
  正解：必须人工抽查，特别是核心逻辑

❌ 反模式 3：跳过自评
  实现完直接合并
  问题：90% 的小 Bug 自评就能发现
  正解：必须有自评阶段

❌ 反模式 4：超大 PR
  一个 PR 包含 5 个功能 + 修 Bug + 重构
  问题：评审困难，难以发现问题
  正解：每个 PR 一个功能，< 500 行

❌ 反模式 5：提示词碎片化
  每次都临时写不同的指令
  问题：质量不稳定，无法沉淀
  正解：用本目录的标准提示词

❌ 反模式 6：忽略测试
  「先把功能跑通，测试以后写」
  问题：以后一定不写
  正解：开发 + 测试必须一起做
```
