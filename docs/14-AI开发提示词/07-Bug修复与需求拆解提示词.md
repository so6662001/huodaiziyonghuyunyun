# 07 - Bug 修复 & 需求拆解提示词

## 一、Bug 修复提示词

```text
任务：修复 Bug

## Bug 卡

| 字段 | 值 |
|---|---|
| Bug ID | BUG-2026-001 |
| 标题 | 创建会话时偶现 NullPointerException |
| 严重级别 | 高/中/低 |
| 影响范围 | 买家端 / 卖家端 / 双端 |
| 复现率 | 100% / 60% / 偶现 |
| 影响版本 | v1.2.3 |

## 现象

[详细描述用户看到的现象]

## 复现步骤

1. ...
2. ...
3. ...

## 日志

```
[2026-05-23 10:15:23] ERROR ... NullPointerException
    at com.huodaizi.session.service.impl.PurchaseSessionServiceImpl.createSession(:88)
    ...
```

## 期望行为

应该 ...

## 实际行为

实际 ...

## 请按以下顺序处理

### Step 1：根因分析（不要立即改代码）

请回答：
1. 这个 Bug 的直接原因是什么？（哪一行代码、哪个变量为 null）
2. 根本原因是什么？（为什么这个变量会是 null？是设计问题还是边界遗漏？）
3. 是否有相似问题（同一根因可能引发其他 Bug）？

### Step 2：影响评估

1. 多少用户受影响？
2. 数据是否已损坏？
3. 是否需要数据修复脚本？
4. 是否需要紧急回滚？

### Step 3：修复方案

提供至少 2 个方案：

方案 A：[描述] 优点... 缺点...
方案 B：[描述] 优点... 缺点...

推荐：方案 X，理由：...

### Step 4：实现修复

按推荐方案修改代码。

### Step 5：编写回归测试

必须新增至少 1 个测试用例，确保此 Bug 不再出现。

### Step 6：验证

- [ ] 本地复现 Bug
- [ ] 应用修复
- [ ] 重新执行复现步骤，确认已修复
- [ ] 跑全量测试，确认未引入新问题

## 自查

□ 根因清晰（不是头痛医头）
□ 影响评估完整
□ 修复代码符合规范
□ 新增回归测试
□ 不破坏既有功能
□ Commit 信息：fix(module): 描述 - close #BUG-ID
□ PR 链接到 Bug Issue
```

## 二、热修复（Hotfix）提示词

```text
任务：热修复线上紧急 Bug

⚠️ 这是紧急修复，直接打在 main 分支并立即发版

## 原则

1. 最小改动原则（只改必须改的）
2. 不做"顺手优化"
3. 必须有完整回归测试
4. 必须有 PRD 负责人批准

## 流程

1. 从 main 切 hotfix 分支：cursor/hotfix-xxx-228e
2. 修复代码（最小化）
3. 写回归测试
4. 紧急评审（不需要排队）
5. 合并 + 立即发版
6. 反向合并到 develop 分支

## 与常规 Bug 修复的差异

| 维度 | 常规 Bug | 热修复 |
|---|---|---|
| 评审 | 走完整流程 | 简化评审 |
| 测试 | 全量回归 | 关键路径回归 |
| 发版 | 等下个版本 | 立即发版 |
| 反向合并 | 不需要 | 必须反向合并到 develop |
```

## 三、需求拆解提示词

```text
任务：把 PRD 拆解为可执行的开发任务

## 输入

PRD 文档：[docs/07-产品PRD-v2/xx.md]

## 输出要求

把 PRD 拆解为「Epic → Story → Task」三层结构。

### Epic（史诗，2-4 周完成）
代表一个完整功能模块。

### Story（用户故事，3-7 天完成）
代表一个用户可感知的价值。
格式：作为 [角色]，我希望 [功能]，以便 [价值]。

### Task（任务，1-3 天完成）
代表一个工程师可独立完成的工作。

## 模板

```
# Epic：M2 采购会话核心模块

## Story 1：买家发起采购会话

作为买家，我希望快速发布需求并自动获得报价，
以便不再依赖电话和微信群。

### 验收标准

1. 买家在 5 步内可发布需求
2. 发布后 30 秒内收到至少 1 个报价
3. 报价质量评分 ≥ 80%

### Tasks

- [ ] Task 1.1：DB 设计 + DDL（estimate: 0.5 天）
- [ ] Task 1.2：API 设计 + OpenAPI（estimate: 0.5 天）
- [ ] Task 1.3：后端 - Entity / Mapper（estimate: 0.5 天）
- [ ] Task 1.4：后端 - Service 层（estimate: 1 天）
- [ ] Task 1.5：后端 - Controller + 测试（estimate: 1 天）
- [ ] Task 1.6：前端 - 发需求页 UI（estimate: 1 天）
- [ ] Task 1.7：前端 - 表单逻辑 + API（estimate: 0.5 天）
- [ ] Task 1.8：联调 + 修 Bug（estimate: 1 天）
- [ ] Task 1.9：编写文档（estimate: 0.5 天）

总估算：6.5 天

### 依赖

- 依赖 M1 用户登录已完成
- 依赖 M3 派单服务（可 Mock）

### 风险

- 风险 1：AI 识变服务尚未稳定，需 Mock
- 风险 2：派单算法需配合调优

## Story 2：AI 自动识变需求

作为买家，我希望在群聊中随口说"明天前要"，
系统自动更新需求，
以便不必重新填表。

[继续展开]

[姓名]

2026-06-01

## 四、技术债盘点提示词

```text
任务：盘点代码库的技术债

## 你的角色

你是技术 Leader，需要识别项目中的技术债，制定还债计划。

## 检查维度

### 1. 代码异味（Code Smell）
- 长方法 > 100 行
- 大类 > 500 行
- 重复代码块
- 复杂条件嵌套（if 嵌套 > 3 层）
- 魔法数字
- 空 catch

### 2. 架构债
- 跨层调用
- 循环依赖
- 上帝类
- 紧耦合
- 应抽象未抽象

### 3. 测试债
- 测试覆盖率低（< 60%）
- 缺失关键场景测试
- 测试质量差（无断言、用 Thread.sleep）

### 4. 性能债
- 已知慢查询未优化
- 缺少缓存
- 同步调用慢服务

### 5. 安全债
- 已知漏洞未修
- 依赖版本陈旧
- 密码硬编码

### 6. 文档债
- 接口无文档
- 复杂逻辑无注释
- README 与现实不符

## 输出格式

```
# 技术债盘点报告

## Top 10 技术债（按 ROI 排序）

| # | 类型 | 位置 | 影响 | 工作量 | ROI | 优先级 |
|---|---|---|---|---|---|---|
| 1 | 性能 | SessionServiceImpl 的 list 接口 N+1 查询 | 高 | 1 天 | 高 | P0 |
| ...

## 偿还计划

- 本月（紧急）：1-3
- 下月（重要）：4-6
- 季度内（一般）：7-10

## 不还的代价

如果不还，预计：
- 性能：响应时间提升 30% → 用户流失
- 维护：每改一次相关代码多花 3x 时间
- 风险：xx 风险概率提升

## 五、迁移 / 重构提示词

```text
任务：重构 / 迁移代码

## 重构卡

| 字段 | 值 |
|---|---|
| 重构目标 | xx |
| 范围 | xxx 模块 |
| 风险等级 | 高 / 中 / 低 |
| 是否影响接口 | 是 / 否 |

## 强制原则

1. **小步快走**：每次 PR 改动 < 500 行
2. **保持绿灯**：每次 PR 后测试必须全过
3. **可回滚**：每个步骤都可独立回滚
4. **平行实现**：先实现新版本，再切流量，最后删旧版本
5. **不混合**：不要"顺手"加新功能或修 Bug

## 阶段

### Phase 1：准备
- [ ] 写 RFC 文档
- [ ] 团队评审
- [ ] 制定回滚预案
- [ ] 准备监控告警

### Phase 2：实现新版本
- [ ] 平行实现（不替换旧的）
- [ ] 写完整测试
- [ ] 在测试环境验证

### Phase 3：切流量
- [ ] 灰度切 1% 流量
- [ ] 观察 1-3 天
- [ ] 切 10% → 50% → 100%

### Phase 4：清理
- [ ] 等待 1-2 周观察期
- [ ] 删除旧代码
- [ ] 删除特性开关

## 风险点（必须告知 Reviewer）

1. ...
2. ...
```
