## 一、PR 级 Checklist（每次 PR 必查）

### 1. 需求层（漏功能就在这里漏）

```
□ PR 描述链接到具体的 PRD 章节
□ PRD 中提到的所有功能点都已实现
□ PRD 中提到的所有"边界状态"都已处理
□ PRD 中提到的所有"错误处理"都已实现
□ PRD 中提到的"性能要求"已达成
□ PRD 中提到的"权限要求"已实现
□ 没有做 PRD 没要求的事（避免范围蔓延）
```

> ⚠️ 50% 的 AI 翻车都因为"漏功能"。开发前必须**逐字读 PRD**，列出所有要点 → 实现完后**逐项打勾**。

### 2. API 契约层

```
□ Controller 路径与 openapi.yaml 完全一致
□ HTTP 方法与 openapi.yaml 一致
□ 请求体 schema 与 openapi.yaml 一致（字段名/类型/必填）
□ 响应体 schema 与 openapi.yaml 一致
□ 错误码使用了 ErrorCode 枚举（不自创）
□ 字段命名 camelCase（不是 snake_case）
□ 时间字段格式 ISO 8601（不是字符串）
□ 金额字段 BigDecimal（不是 double）
□ 枚举字段是 String（不是 number）
□ 列表接口分页（PageResult）
□ 接口有 @Operation + @Tag 注解
```

### 3. 数据库层

```
□ Entity 字段名与 DDL 完全一致
□ Entity 类型与 DDL 完全一致
□ 所有外键关系正确
□ 用了 @TableName / @TableId 注解
□ JSON 字段用了 JacksonTypeHandler
□ 查询用了 LambdaQueryWrapper（不拼 SQL）
□ 列表查询有索引（去查 DDL 验证）
□ 写操作有事务（@Transactional）
□ 没有在事务中调用外部服务
□ 没有 N+1 查询（在循环里查 DB）
```

### 4. 业务逻辑层

```
□ 业务规则与 PRD 一致（引用 PRD 段落证明）
□ 边界值处理（null / 空 / 越界 / 重复）
□ 异常路径用 BusinessException + ErrorCode
□ 重复提交处理（idempotencyKey）
□ 并发处理（如需）
□ 状态机迁移合法（不能跳过中间状态）
□ 用户身份从 SecurityUtils 拿（不从前端传）
□ 数据隔离（用户只能访问自己的数据）
```

### 5. UI/UX 层（前端 PR 必查）

```
□ 颜色全部用 token（无硬编码）
□ 字号全部用 token，最小 12px
□ 间距都是 4 的倍数
□ 按钮最小 44pt
□ 圆角符合规范（按钮 8 / 卡片 12 / 标签 4）
□ 阴影用 token（sm / md / lg）
□ 包含默认 / 加载 / 空 / 错 / 成功 状态
□ 移动端 375 / 414 双适配
□ 长文本省略
□ 数字千分位
□ 价格保留 2 位小数
□ 时间相对显示
□ 图片加载失败 fallback
□ 表单防双击
□ 表单有验证
□ 错误提示是人话
□ 关键操作有二次确认
```

### 6. 权限与安全

```
□ 所有 Controller 默认 @SaCheckLogin（除登录）
□ 管理员接口有角色检查
□ 用户身份从 SecurityUtils 拿
□ 数据隔离（用 SQL WHERE buyer_id = currentUserId 等）
□ 敏感字段脱敏（手机号 / 身份证 / 银行卡）
□ 没有 SQL 注入（用参数化查询）
□ 没有 XSS（用户输入转义）
□ 日志中无密码 / token / 完整手机号
□ 配置中无硬编码密钥
□ 文件上传有类型 + 大小 + 文件名检查
□ 敏感接口有频控（短信 / 登录）
```

### 7. 性能层

```
□ 列表接口分页（默认 20，最大 100）
□ 列表查询有索引
□ 高频读接口有 Redis 缓存
□ 缓存 key 设计合理 + 过期时间 + 防雪崩
□ 远程调用有超时（默认 3s）
□ 慢服务调用走异步（MQ）
□ 没有循环里查 DB（N+1）
□ 大对象不缓存（OOM 风险）
□ 集合大小有上限
```

### 8. 日志与监控

```
□ 关键路径有 log.info（创建、修改、删除）
□ 异常有 log.error + 完整堆栈
□ 日志含 requestId（链路追踪）
□ 敏感字段已脱敏
□ 没有 System.out / console.log 残留
□ 没有 e.printStackTrace()（用 log.error）
□ 业务指标埋点（如转化率统计）
```

### 9. 测试层

```
□ 单元测试覆盖率 ≥ 80%
□ Controller 测试每个接口 ≥ 3 个用例（正常 + 异常 + 权限）
□ 边界值测试（null / 0 / 最大值）
□ 异常路径测试（每个 throw 都测）
□ 测试名清晰（@DisplayName 中文）
□ 测试独立（不依赖顺序）
□ 测试可重复（不依赖时间 / 网络）
□ mvn test 通过
□ 关键业务流程有 E2E 测试
```

### 10. 代码质量

```
□ 类名 / 方法名 / 字段名清晰
□ 单方法不超过 50 行
□ 单类不超过 500 行
□ 圈复杂度 ≤ 10
□ 嵌套深度 ≤ 3
□ 没有重复代码（DRY）
□ 没有魔法数字（提到常量 / 配置）
□ 没有 TODO / FIXME 未处理
□ 没有注释掉的废代码
□ 使用了 Lombok 减少样板
□ 使用了 MapStruct（不要 BeanUtils.copyProperties）
□ 公共方法有 Javadoc
□ 复杂逻辑有注释（解释为什么）
```

### 11. 文档

```
□ Controller 有 @Tag + @Operation
□ Swagger 文档生成正常
□ PR 描述完整（背景 / 改动 / 影响 / 测试）
□ 复杂改动有架构图（Mermaid / 图片）
□ README 已更新（如适用）
□ 配置项变更有说明
□ DB 变更有迁移脚本
```

### 12. Git 规范

```
□ 分支名 cursor/xxx-228e 格式
□ 每个 Commit 是逻辑独立的改动
□ Commit 信息符合 Conventional Commits
  feat: / fix: / refactor: / test: / docs: / chore:
□ 没有 Merge 提交污染主线
□ 没有 Force Push（除非协商）
```

## 三、漏功能的常见情形

整理给 AI 看，让它特别小心：

### 情形 1：忽略"边界状态"

```
PRD 写："买家可以撤回未确认的需求"
AI 实现：只实现了创建，没实现撤回

防范：开发前必须扫描 PRD 中所有动词
  - 创建 → 实现
  - 修改 → 实现
  - 删除/撤回 → 实现
  - 关闭 → 实现
  - ......
```

### 情形 2：忽略"错误处理"

```
PRD 写："数量必须 > 0"
AI 实现：只校验非空，没校验大于 0

防范：开发前必须列出所有校验规则
  字段：quantity
  规则：必填 + > 0 + ≤ 1000000
  错误码：xxx
```

### 情形 3：忽略"权限边界"

```
PRD 写："会话只能由发起人关闭"
AI 实现：任何人都能关闭

防范：必须读 PRD 的"权限矩阵"小节
```

### 情形 4：忽略"性能要求"

```
PRD 写："列表查询 P95 < 300ms"
AI 实现：能查就行，没考虑性能

防范：开发前必须读"非功能性需求"
```

### 情形 5：忽略"通知"

```
PRD 写："会话创建后通知所有匹配卖家"
AI 实现：只创建了会话，没发通知

防范：必须扫描 PRD 中所有"通知"关键词
  - 通知
  - 推送
  - 提醒
  - 短信
  - 微信消息
```

### 情形 6：忽略"埋点"

```
PRD 写："统计买家发需求转化率"
AI 实现：没埋任何事件

防范：必须读"数据需求"小节
```

### 情形 7：忽略"日志"

```
PRD 隐含：关键操作要有审计日志
AI 实现：完全没打 log

防范：默认所有 Service 方法第一行 log.info
```

### 情形 8：忽略"配置"

```
PRD 写："议价上限 5 轮（可配置）"
AI 实现：硬编码 5

防范：所有数字都要追问"是否要可配置"
```

## 四、PRD 阅读 SOP

避免漏功能的关键是**正确读 PRD**：

```
Step 1：通读一遍
  目的：了解整体功能

Step 2：扫描所有动词
  创建 / 修改 / 删除 / 撤回 / 关闭 / 接受 / 拒绝 / 转发 / 通知
  → 每个动词都要实现

Step 3：扫描所有数字
  最大 100 / 最小 0 / 5 轮 / 30 秒 / 7 天
  → 每个数字都是规则，必须实现校验

Step 4：扫描所有时间
  立即 / 异步 / 30 秒内 / 1 小时后
  → 决定同步还是异步

Step 5：扫描所有"if/否则"
  如果未登录 / 否则报错 / 否则降级
  → 每个 if 都是异常路径，必须测试

Step 6：扫描所有"通知"
  通知卖家 / 提醒买家 / 推送给管理员
  → 每个通知都要实现

Step 7：扫描所有"统计"
  统计转化率 / 计算 GMV / 看板数据
  → 每个统计都要埋点

Step 8：扫描"非功能性需求"
  性能 / 安全 / 可用性 / 兼容性

Step 9：列出所有功能点 → 实现 → 打勾

Step 10：让产品 / Reviewer 对照检查
```

## 五、Definition of Done（完成的定义）

```
一个任务 "完成"的标准：

✅ 代码完成
✅ 单元测试 ≥ 80% 覆盖
✅ 集成测试通过
✅ Code Review 通过（人工 + AI）
✅ 安全扫描通过
✅ 性能测试通过（关键接口）
✅ 接入了监控告警
✅ 完成了对应文档更新
✅ PR 描述包含本 Checklist 的完成情况
✅ 测试环境部署成功
✅ 产品 / QA 验收通过

没有这 11 项全部完成的 PR，不允许合并。
```
