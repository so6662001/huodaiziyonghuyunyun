# 14 - 多规格红线（业务底层约束）

> **多规格是货袋子产品的"灵魂"**。一旦在任何环节退化为单条规格，整个产品价值崩塌。
> 本文档列出 AI 在数据/接口/UI/逻辑层面对多规格的所有强制约束。

---

## 一、为什么必须坚持多规格

```
钢贸真实场景：
- 80%+ 询价是 5-30 行规格的清单（一个项目的整套钢材）
- 卖家可能只能供其中 3-5 行（专精品类）
- 买家希望一次性收到对比表，AI 给出最优组合
- 已成交的行立即锁价，剩余继续询价（不能阻塞）

如果退化为单条：
❌ 真实场景覆盖率 < 20%
❌ 采购员要发 8 次单（30 分钟+）
❌ 无法做最优组合
❌ 无法按行成交
❌ 整个 v2 产品价值崩塌
```

## 二、数据层红线

### 2.1 DemandCard.items 必须是数组

```java
// ✅ 正确
public class DemandCard {
    private List<DemandItem> items;  // 数组
}

// ❌ 禁止
public class DemandCard {
    private DemandItem item;          // 不能改成单值
    private String productType;       // 不能把字段平铺到 card
}
```

### 2.2 行号 itemNo 必须稳定

```
原则：删除某行后，已有行的 itemNo 不变；新增行用最大号 + 1

例：原 [1, 2, 3, 4]
   删除 2 → [1, 3, 4]（不能重排成 [1, 2, 3]）
   再加 1 行 → [1, 3, 4, 5]

理由：
- 卖家报价、订单、发货都按 itemNo 引用
- 重排会导致历史数据错乱
- AI 识变"修改第 3 行"必须能准确定位
```

### 2.3 字段命名规范

```
✓ 必须用 items（数组）
✓ 必须用 itemNo（行号，不是 itemIndex 或 rowNumber）
✓ 必须用 quantity + quantityUnit（数量+单位分开）
✓ 必须用 spec（规格对象，含 thickness/width/length 等）
✓ 必须用 targetPriceRangeMin + targetPriceRangeMax（价格区间）

❌ 严禁用 specifications（用 items）
❌ 严禁用 itemId（用 itemNo）
❌ 严禁用 size（用 spec）
❌ 严禁用 price（必须明确 targetPrice / quotePrice / unitPrice）
```

### 2.4 整单字段 vs 行级字段

```
整单级（DemandCard 上）：
- sessionId / version / changedFields
- defaults.deliveryCity（默认到货地）
- defaults.deliveryDeadline（默认交期）
- defaults.paymentTerms（默认账期）
- splitStrategy（拆单策略）
- note（整单备注）

行级（DemandItem 上）：
- itemNo / productType / materialGrade / spec / quantity
- 行级到货地（可覆盖 defaults.deliveryCity）
- 行级交期（可覆盖 defaults.deliveryDeadline）
- 行级目标价
- 行级质量要求
- 行级备注

⚠️ 行级字段若为空，回退到 defaults 对应值
```

## 三、接口层红线

### 3.1 创建会话接口必须接收 items 数组

```http
POST /api/v1/sessions
Content-Type: application/json

{
  "items": [                              ← ⭐ 必须是数组
    {
      "itemNo": 1,
      "productType": "plate",
      "materialGrade": "Q235B",
      "spec": {"thickness": 5.5, "width": 1500},
      "quantity": 50,
      "quantityUnit": "ton",
      "deliveryCity": "天津",
      "targetPriceRangeMax": 3950
    },
    { "itemNo": 2, ... },
    ...
  ],
  "defaults": {
    "deliveryDeadline": "2026-05-30T00:00:00+08:00",
    "paymentTerms": "cash"
  },
  "splitStrategy": "auto"
}
```

### 3.2 卖家报价接口必须支持多行批量

```http
POST /api/v1/quotes

{
  "sessionId": "ps_240527001",
  "items": [
    { "itemNo": 1, "unitPrice": 3920, "quantity": 50 },
    { "itemNo": 2, "unitPrice": 3980, "quantity": 30 },
    { "itemNo": 3, "unitPrice": 4080, "quantity": 60 }  // 部分供货
    // 不报第 5/6/7/8 行
  ],
  "validUntil": "2026-05-27T15:00:00+08:00",
  "paymentTerms": "cash"
}
```

**红线**：禁止"每行单独发起一个 POST /api/v1/quotes 调用 N 次"——这会破坏卖家"整批报价"语义。

### 3.3 订单按行操作（不是整单操作）

```http
✓ 按行发货
POST /api/v1/orders/o_001902/items/1/ship

✓ 按行确认收货
POST /api/v1/orders/o_001902/items/1/receive

✓ 按行申诉
POST /api/v1/appeals
{ "orderId": "o_001902", "itemNo": 2, ... }

❌ 禁止只支持整单发货：
POST /api/v1/orders/o_001902/ship  ← 必须支持按行 + 整单两种粒度
```

### 3.4 响应必须包含每行状态

```json
{
  "sessionId": "ps_240527001",
  "currentCard": {
    "items": [
      {
        "itemNo": 1,
        "status": "deal",           ← ⭐ 每行独立状态
        "matchedQuoteCount": 5,
        ...
      },
      {
        "itemNo": 2,
        "status": "quoted",
        "matchedQuoteCount": 4,
        ...
      },
      ...
    ]
  }
}
```

## 四、UI 层红线

### 4.1 发需求页（移动端 01 / PC 端 02）

```
✓ 必须默认即多规格录入界面
✓ 必须支持 Excel/拍照/语音/复用上次 4 种快速录入
✓ 必须有"+ 添加规格行"按钮
✓ 必须支持行内编辑（不弹窗）
✓ 必须有"整单 + 行级"两层信息架构

❌ 禁止"单条表单 + 高级选项"老 UI
❌ 禁止把行数限制在 1 个
❌ 禁止"必须填完所有字段才能加新行"
```

### 4.2 采购会话页（移动端 03 / PC 端 03）

```
✓ 必须按行展示进展（8 行 = 8 个独立卡片/行）
✓ 每行必须有独立状态标识：
  - pending（待派单）
  - dispatching（派单中）
  - quoted（已报价，可选）
  - locked（已锁价）
  - deal（已成交）
  - no_supply（无供应）
✓ 必须支持"整单进展摘要"（5/8 行已报价）
✓ 必须支持 AI 整单优化建议（合并/改规/扩区域）

❌ 禁止把所有行平铺成一条"询价"
❌ 禁止整单状态覆盖行级状态
```

### 4.3 卖家接单页（移动端 04 / PC 端 02）

```
✓ 必须按行展示买家需求
✓ 每行必须显示"您库存"对比（现货/部分/无货）
✓ 必须支持勾选可供货行（部分供货）
✓ 必须支持"仅报部分数量"（库存不足时）
✓ 必须支持"改规建议"（向买家提议替代规格）

❌ 禁止"全报或不报"的二选一
❌ 禁止隐藏卖家无货的行（应该灰显，可见但不可勾选）
```

### 4.4 报价矩阵（移动端 05 / PC 端 04）

```
PC 端必须实现完整 N 卖家 × M 行 矩阵：
✓ 横轴：所有报价卖家
✓ 纵轴：所有规格行
✓ 单元格：报价 / 无供应（—）
✓ 高亮：最低价（金色）/ 次优（绿色）
✓ 底部：每家"能供条数"、"小计"、"综合分"
✓ AI 最优组合方案（多家分单）

移动端简化版：
✓ 按规格行展示 Top 3-5 卖家
✓ 各行可下钻看完整对比

❌ 禁止只展示最低价（必须有完整矩阵）
❌ 禁止只支持"单家整单成交"
```

### 4.5 订单详情（移动端 10 / PC 端 07）

```
✓ 多规格订单必须按行展示
✓ 每行独立显示：订单数量/已收/待收/差异
✓ 物流可能分批（一个订单 2 个运单号）
✓ 验收按行独立
✓ 申诉按行独立

❌ 禁止把多规格订单展示成"总金额 + 总吨数"
```

## 五、业务逻辑红线

### 5.1 AI 识变必须识别"哪一行"

```
买家说："3 号规格再加 20 吨"
AI 必须识别：
  intent: quantity_change
  changes: [
    {
      itemNo: 3,           ← ⭐ 必须定位到具体行
      field: "quantity",
      oldValue: 100,
      newValue: 120
    }
  ]

买家说："交期改成明天"
AI 必须识别：
  intent: delivery_change
  changes: [
    {
      itemNo: null,         ← null 表示整单变更
      field: "defaults.deliveryDeadline",
      oldValue: "2026-05-30",
      newValue: "2026-05-28"
    }
  ]
```

### 5.2 行级独立成交

```
场景：8 行规格，5 行已收到报价，3 行还没有

✓ 必须允许买家先锁定 5 行成交
✓ 已成交的 5 行立即"锁价"状态
✓ 剩余 3 行继续派单、继续询价
✓ 同一 sessionId 内可以分多个订单创建

❌ 禁止"必须 8 行都谈妥才能成交"
❌ 禁止"锁价后整单冻结"
```

### 5.3 拆单策略必须实现 3 种

```
auto（智能拆单，默认）：
- 系统按 品类+区域 自动拆分
- 例：8 行 → 板材给天津池、螺纹给唐山池、其他给全网
- 可分多家成交

bundle（整单打包）：
- 仅推送给"能供全部 N 行"的卖家
- 适合需要单一开票场景

manual（手动拆）：
- 买家指定哪几行打包给同一卖家
- 用于跨品类长期合作的供应商
```

### 5.4 议价上限（PRD 第 X.Y 节硬规定）

```
- 单次会话变更次数 ≤ 5 次（changeCount）
  超过自动锁定，必须重新创建会话
- 单次报价议价轮数 ≤ 5 次
  超过自动放弃，进入超时
- 报价有效期默认 60 min，可配置 30-120 min
- 派单等待 30 min 无报价自动扩池
- 锁价持续 60 min，不付款自动解锁
```

## 六、AI 自检清单（多规格专项）

每次产出代码或 UI 后，必须输出以下自检：

```
□ DemandCard 含 items 数组（不是单值）
□ DemandItem 有 itemNo 字段
□ itemNo 在删除/新增后保持稳定
□ 整单字段与行级字段分层正确
□ API 接收 items 数组（不是单条接口）
□ API 响应每行带 status
□ UI 默认即多规格录入
□ UI 按行展示进展和状态
□ 卖家可勾选部分行 + 部分数量
□ 支持 AI 按行识变
□ 支持行级独立成交
□ 支持 3 种拆单策略（auto/bundle/manual）
□ 矩阵对比展示所有 N×M 单元格
□ 文案中没有"询价"暗示单条（必须说"清单"）
```

## 七、典型反例与正解

### 反例 1：把多规格当数组遍历单条 API

```java
// ❌ 错误
for (DemandItem item : items) {
    quoteService.createQuote(buyer, item);  // 调用 N 次
}

// ✅ 正确
quoteService.createBatchQuote(buyer, items);  // 一次调用
```

### 反例 2：UI 只展示第一行

```vue
<!-- ❌ 错误 -->
<div>
  规格：{{ session.items[0].productType }}
  数量：{{ session.items[0].quantity }}
</div>

<!-- ✅ 正确 -->
<div v-for="item in session.items" :key="item.itemNo">
  <SpecRow :item="item" :status="item.status" />
</div>
<div>共 {{ session.items.length }} 行规格</div>
```

### 反例 3：状态只有整单

```java
// ❌ 错误
public class Session {
    private String status;  // 只有整单状态
}

// ✅ 正确
public class Session {
    private String overallStatus;  // 整单状态（聚合视图）
    private List<DemandItem> items; // 每行独立 status
}

// 整单状态计算逻辑：
if (所有行 == "deal") return "deal";
if (任意行 == "no_supply" && 其他都 done) return "partial_deal";
if (任意行 == "quoted") return "quoting";
return "matching";
```

### 反例 4：硬编码行数限制

```javascript
// ❌ 错误
if (items.length > 1) {
  alert('一次只能询 1 个规格');
}

// ✅ 正确
if (items.length > 100) {  // 上限 100
  throw new BusinessException(ErrorCode.ITEMS_TOO_MANY, '一次最多 100 行');
}
```
