# 15 - 页面对应与不走样规范

> 38 页原型（移动端 20 + PC 端 18）的**一致性强制规范**。

## 二、字段名一致性铁律

所有端必须用**完全一致**的字段名（来自 OpenAPI 和 DDL）：

### 2.1 高频字段

```
✓ sessionId（不是 session_id / sessionID / sid）
✓ items（不是 itemList / list / specs）
✓ itemNo（不是 itemId / index / rowNo）
✓ quantity / quantityUnit（数量+单位分开）
✓ productType（不是 category / type）
✓ materialGrade（不是 material / grade）
✓ spec（对象，含 thickness/width/length/diameter）
✓ deliveryCity / deliveryDeadline
✓ targetPriceRangeMin / targetPriceRangeMax（注意 Min/Max 后缀）
✓ unitPrice（报价时）
✓ orderId / orderItemNo
✓ buyerCompanyId / sellerCompanyId
```

### 2.2 字段命名规范

```
JSON / JS / TS：camelCase
  - sessionId, currentCardId, deliveryDeadline

SQL / DB：snake_case
  - session_id, current_card_id, delivery_deadline

Java 字段：camelCase + JPA 注解映射 snake_case
  - private String sessionId;
  - @Column(name = "session_id")

CSS：kebab-case
  - .spec-row, .list-card, --primary-color
```

## 三、状态/枚举一致性铁律

### 3.1 跨端必须用相同字符串

```
会话状态（SessionStatus）：
  active / matching / quoting / negotiating / deal / expired / closed / cancelled

行级状态（DemandItem.status）：
  pending / dispatching / quoted / locked / deal / no_supply

报价状态（QuoteStatus）：
  active / updated / expired / withdrawn / won / lost / superseded

订单状态（OrderStatus）：
  created / paid / shipping / partial_shipped / shipped / received / completed / refund

发货状态（ShipmentStatus）：
  pending / picking / in_transit / delivered / signed / exception

申诉状态（AppealStatus）：
  submitted / investigating / mediating / resolved / rejected / appealed
```

### 3.2 显示文案对应表（两端必须一致）

| 枚举值 | 显示文案（中文）| 移动端 | PC 端 |
|---|---|---|---|
| `pending` | 待派单 | ✓ | ✓ |
| `dispatching` | 派单中 | ✓ | ✓ |
| `quoted` | 已报价 | ✓ | ✓ |
| `locked` | 已锁价 / ✓ 锁定 | ✓ | ✓ |
| `deal` | 已成交 | ✓ | ✓ |
| `no_supply` | 无供应 | ✓ | ✓ |
| `urgent` | 加急 / 紧急 | ✓ | ✓ |
| `bounty` | 悬赏 | ✓ | ✓ |

**红线**：不能一端叫"备货中"另一端叫"准备中"——必须统一"备货发货中"。

## 五、跨端业务逻辑一致性

### 5.1 数据流必须共享

```
PC 端创建的会话 → 移动端能看到（实时同步）
PC 端修改的报价 → 移动端能立即看到
移动端的草稿 → PC 端能继续编辑

实现：
✓ 共用同一组后端 API
✓ 共用同一个数据库
✓ 共用同一个 Token 鉴权
✓ 移动端 PC 端可同时登录同账号
```

### 5.2 业务规则不能分歧

```
✓ 议价 5 轮上限 → 两端都强制
✓ 报价有效期 60 min → 两端都强制
✓ 单清单最多 100 行 → 两端都强制
✓ 加急 ¥9.9 / 悬赏 ¥99 → 两端定价一致
✓ 卖家分级阈值 → 两端显示一致
```

### 5.3 实时性要求

```
高频操作必须实时同步（< 3 秒）：
- 新询价到达
- 新报价提交
- 议价回复
- 订单状态变更
- 发货 / 收货确认

中频操作（< 30 秒）：
- 库存更新
- 客户分级变化

低频操作（< 5 分钟）：
- KPI 统计
- 趋势图数据
```

## 七、禁止"端分裂"的反模式

### ❌ 反例 1：字段名不同

```javascript
// 移动端
{ sessionId: "ps_001", items: [...] }

// PC 端
{ session_id: "ps_001", item_list: [...] }  // ❌ 端分裂！
```

### ❌ 反例 2：状态值不同

```
// 移动端用 quoted
status === 'quoted'

// PC 端用 has_quote
status === 'has_quote'  // ❌ 端分裂！
```

### ❌ 反例 3：文案不同

```
// 移动端按钮："立即报价"
// PC 端按钮："开始报价"  // ❌ 端分裂！

// 移动端状态："待发货"
// PC 端状态："准备发货"  // ❌ 端分裂！
```

### ❌ 反例 4：业务规则不同

```
// 移动端校验：行数 ≤ 100
if (items.length > 100) ...

// PC 端校验：行数 ≤ 200  // ❌ 端分裂！
if (items.length > 200) ...
```

### ❌ 反例 5：颜色含义不同

```css
/* 移动端 */
.urgent { color: red; }    /* 紧急 = 红色 */

/* PC 端 */
.urgent { color: orange; } /* 紧急 = 橙色 ❌ 端分裂！ */
```

### ✅ 正解：通过共享层强制统一

```
1. 共享类型定义（TypeScript 接口 / Java DTO）
2. 共享枚举（生成器统一生成两端代码）
3. 共享文案表（i18n JSON 文件，两端引用）
4. 共享 Token（CSS 变量 / SCSS 变量两端引用）
5. 共享验证规则（@Valid 注解 + 前端 JSON Schema）
```

## 八、新增页面强制流程

```
开发任何新页面（无论哪端）：

Step 1：先查另一端是否有对应页面
        → 如果有，本次必须 100% 对齐
        → 如果没有，本次先在双端都设计原型

Step 2：在 PRD 中找到对应章节
        → 引用具体段落
        → 列出涉及的字段和状态

Step 3：在 OpenAPI 中找到接口
        → 不存在则先定义再实现

Step 4：在 DDL 中找到表/字段
        → 不存在则先 RFC 再加表

Step 5：复用既有组件
        → 优先复用 styles.css / styles-pc.css 既有 class
        → 实在没有再扩展（不写一次性内联样式）

Step 6：写代码

Step 7：双端对照自检（输出对照表）
```
