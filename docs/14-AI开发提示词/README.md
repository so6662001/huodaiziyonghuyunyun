# 货袋子 AI 开发提示词工程包

> **目的**：让 AI（Cursor / Claude Code / GitHub Copilot / GPT）开发货袋子项目时，**保证不漏功能、不跑偏、符合规范、可直接交付**。

## 一、为什么要做提示词工程？

```
没有提示词工程的 AI 开发：
  开发者：「帮我写个发需求页面」
  AI：（生成一个看起来还行但不符合规范、缺关键字段、风格随意的代码）
  开发者：再改 30 轮，最终还是要自己重写

有提示词工程的 AI 开发：
  开发者：粘贴标准提示词 + 任务卡 →
  AI：直接产出符合 PRD + 设计规范 + 代码规范 +
       自带测试 + 自带验收清单的可交付代码
  开发者：评审 1-2 轮即可合并
```

**ROI 数据**：标准化提示词可减少 60-70% 的返工，提升 3x 开发速度。

## 四、使用流程（必读）

### 4.1 项目级一次性配置

```
1. 在仓库根目录创建 .cursorrules 文件
2. 把【00-核心系统提示词.md】完整复制进去
3. Cursor 会自动在每次对话时附带这些规则
```

### 4.2 每个任务开始前

```
Step 1: 打开对应任务类型的提示词模板（如 templates/新增功能-后端.txt）
Step 2: 填入【任务卡片】（PRD 链接、API 编号、验收标准）
Step 3: 粘贴给 AI，等待产出
Step 4: 对照【10-验收checklist.md】逐项核验
Step 5: 不通过则用【06-代码评审提示词.md】让 AI 自评 + 改
```

### 4.3 每次提交 PR 前

```
1. 对照【10-验收checklist.md】所有项目打勾
2. 使用【05-测试用例生成提示词.md】让 AI 补测试
3. 使用【06-代码评审提示词.md】让 AI 自评 + 修复
4. PR 描述中链接：实现的需求 / 通过的 checklist 项
```

## 六、对项目 ROI 的预期

| 不用提示词工程 | 用提示词工程 |
|---|---|
| 1 个功能开发 2-3 天 | 1 个功能开发 4-8 小时 |
| 5-10 次修改才合格 | 1-2 次修改即合格 |
| 风格随机、字段易漏 | 风格统一、字段齐全 |
| 缺测试、缺文档 | 自带测试 + 文档 |
| PR 评审耗时 1-2 小时 | PR 评审 15-30 分钟 |

## 七、维护与迭代

```
提示词不是一次性产物，要持续迭代：

1. 每次 AI 产出"翻车"，先看是哪个提示词没说清
2. 把"翻车经验"加到对应提示词的"反模式"段
3. 每月评审一次提示词的有效性
4. 团队新人入职必须先读完本目录
5. 提示词版本化管理（在文件头标注 v1.0/v1.1...）
```

## 八、紧急情况

```
AI 开发翻车的常见原因 + 应对：

❌ AI 编造不存在的字段
  → 检查【00 系统提示词】是否引用了 DDL/OpenAPI
  → 强制要求 AI 在动手前回答："字段从哪个文档来？"

❌ AI 凭空创造 API
  → 检查【04 API 开发提示词】
  → 强制要求 AI 在动手前先列出涉及的 API 编号

❌ AI 写的页面风格不一致
  → 检查【03 UI 高保真还原提示词】
  → 强制要求 AI 在动手前列出使用的 design token

❌ AI 漏掉关键业务规则
  → 检查【10 验收 checklist】
  → 强制要求 AI 在动手前先回答 PRD 里的"边界状态"
```
