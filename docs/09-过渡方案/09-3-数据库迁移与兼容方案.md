# 数据库迁移与兼容性方案

> 配套 `09-1-双引擎过渡方案.md`。**给技术团队的具体迁移指南**。

## 一、原则

1. **零停机**：所有迁移在线完成
2. **可回滚**：每个变更都有逆操作
3. **向后兼容**：老 API 完全不动
4. **数据共享**：新旧表通过 view / 触发器 / 应用层桥接

## 二、迁移阶段

### Phase 1：扩展现有表（M1）

**给现有库存表加新字段**，不破坏旧逻辑：

```sql
-- 现有 inventory 表（推测的字段，根据实际调整）
-- 扩展新字段，全部带默认值，不影响旧代码

ALTER TABLE inventory
  ADD COLUMN accept_inquiry BOOLEAN DEFAULT TRUE
    COMMENT '接询价开关',
  ADD COLUMN matched_count INT DEFAULT 0
    COMMENT '被询价匹配次数',
  ADD COLUMN last_matched_at DATETIME DEFAULT NULL
    COMMENT '最后被匹配时间',
  ADD COLUMN inquiry_priority TINYINT DEFAULT 5
    COMMENT '接单优先级（1-10，越大越优先）',
  ADD COLUMN auto_quote_enabled BOOLEAN DEFAULT FALSE
    COMMENT '是否启用自动报价（M9+ 功能）';

CREATE INDEX idx_inventory_accept_inquiry
  ON inventory(accept_inquiry, status, product_category);
```

**回滚方案**：

```sql
ALTER TABLE inventory
  DROP COLUMN accept_inquiry,
  DROP COLUMN matched_count,
  DROP COLUMN last_matched_at,
  DROP COLUMN inquiry_priority,
  DROP COLUMN auto_quote_enabled;
```

### Phase 2：新建采购会话相关表（M1-M2）

```sql
-- 全部 33 张新表，详见 docs/08-技术交付物/db/01-schema.sql
```

### Phase 3：建立数据桥接（M2）

**关键工作**：让"库存数据"自动流入"询价匹配池"。

```sql
-- 创建 view，方便询价系统读取库存
CREATE OR REPLACE VIEW v_inventory_for_dispatch AS
SELECT
  i.id AS inventory_id,
  i.seller_id,
  i.product_category,
  i.material_grade,
  i.spec,
  i.available_quantity,
  i.unit_price,
  i.delivery_location,
  i.created_at,
  -- 关联卖家信息
  c.city AS seller_city,
  c.verified AS seller_verified,
  cs.current_score AS seller_credit_score,
  cs.level AS seller_level,
  -- 接单偏好
  i.accept_inquiry,
  i.inquiry_priority,
  sp.accept_pools,
  sp.daily_max
FROM inventory i
JOIN user_company_mappings ucm ON ucm.user_id = i.seller_id AND ucm.role = 'owner'
JOIN companies c ON c.company_id = ucm.company_id
LEFT JOIN credit_scores cs ON cs.user_id = i.seller_id AND cs.role = 'seller'
LEFT JOIN seller_preferences sp ON sp.seller_id = i.seller_id
WHERE
  i.status = 'active'
  AND i.accept_inquiry = TRUE
  AND i.available_quantity > 0;
```

询价派单时直接查这个 view，**不影响原 inventory 表**。

### Phase 4：触发器（可选，M3）

当库存被询价匹配时，**自动更新统计字段**：

```sql
-- 当 dispatches 表新增记录时，更新 inventory 的 matched_count
DELIMITER //
CREATE TRIGGER trg_update_inventory_match
AFTER INSERT ON dispatches
FOR EACH ROW
BEGIN
  -- 通过 session_id 找到关联的库存
  UPDATE inventory
  SET
    matched_count = matched_count + 1,
    last_matched_at = NOW()
  WHERE seller_id = NEW.seller_id
    AND status = 'active'
    AND product_category = (
      SELECT product_category FROM demand_cards
      WHERE session_id = NEW.session_id AND is_current = TRUE
    );
END;//
DELIMITER ;
```

**注意**：触发器有性能开销，高并发时建议改为异步消息（Kafka）处理。

### Phase 5：双写阶段（M3-M5）

灰度期，**新功能用新表，但同步写入旧表的部分字段**（如果有重叠）：

```python
# 应用层示例代码
def handle_inquiry_dispatch(session_id, seller_id):
```

## 三、API 兼容性

### 3.1 版本管理策略

```
路径前缀：
  /v1/*  原有 API（保留）
  /v2/*  新 API（双引擎模块）

请求头：
  X-API-Version: 1.0 | 2.0

灰度策略：
  - 客户端代码同时支持 v1 和 v2
  - 通过 feature flag 控制使用哪个
  - 老客户端继续用 v1 不动
```

### 3.2 关键 API 兼容映射

| 老 API（v1） | 新 API（v2） | 兼容关系 |
|---|---|---|
| GET /v1/inventory | GET /v2/products | 数据共享，字段升级 |
| POST /v1/inventory | POST /v2/products | 内部互转 |
| POST /v1/contact | POST /v2/purchase-sessions | 新 API 更结构化 |
| GET /v1/seller-profile | GET /v2/users/{id} | 字段升级 |

**关键设计**：

- 老 API 调用时，**后端同时写入新表**（避免数据分裂）
- 新 API 调用时，**也能读取旧表数据**（向后兼容）

### 3.3 客户端处理

```typescript
// 小程序端示例
class ApiClient {
  async getProducts() {
    // 优先用 v2，失败时降级 v1
    try {
      return await this.fetch('/v2/products');
    } catch (error) {
      console.warn('v2 failed, fallback to v1');
      return await this.fetch('/v1/inventory');
    }
  }
}
```

## 四、灰度策略

### 4.1 Feature Flag 实现

```yaml
# 配置中心（Nacos）
features:
  new_session_engine:
    enabled: true
    rollout:
      mode: percentage
      value: 5    # M3 灰度 5%
    whitelist:    # 种子用户立即开启
      - u_test_seller_001
      - u_test_seller_002

  ai_intent_detection:
    enabled: false  # M4 才开
    rollout:
      mode: percentage
      value: 0

  list_upload:
    enabled: false  # M5 才开
```

### 4.2 应用层代码

```python
def is_feature_enabled(feature_name, user_id):
    config = nacos.get_config(f'features.{feature_name}')
    if not config.enabled:
        return False

    # 白名单优先
    if user_id in config.whitelist:
        return True

    # 灰度百分比
    if config.rollout.mode == 'percentage':
        hash_val = hash(user_id) % 100
        return hash_val < config.rollout.value

    return False


# 使用
@app.route('/api/some-endpoint')
def some_handler():
    if is_feature_enabled('new_session_engine', current_user.id):
        return new_logic()
    else:
        return old_logic()
```

## 五、数据一致性保障

### 5.1 关键场景

#### 场景 A：卖家发库存 → 自动加入询价匹配池

```python
# 旧逻辑（v1）：保持不变
def create_inventory(seller_id, product, ...):
    inv = Inventory.create(...)
    # 旧逻辑结束

# 新增逻辑（应用层添加，无需改老 API）
def create_inventory(seller_id, product, ...):
    inv = Inventory.create(...)
    # ✨ 新增：发到 Kafka，让派单引擎感知
    kafka.publish('inventory.created', {
        'inventory_id': inv.id,
        'seller_id': seller_id,
        'product': product,
        ...
    })
    # ✨ 新增：定时任务自动匹配已发布的询价
    inquiry_matcher.try_match_existing_inquiries(inv)
```

#### 场景 B：买家发询价 → 优先推送已有库存的卖家

```python
def dispatch_session(session):
    # Step 1: 找有库存的卖家（高匹配度）

    # Step 2: 给有库存的卖家高匹配分
    for seller_id in sellers_with_inventory:
        score_bonus = 20  # 有库存加 20 分

    # Step 3: 正常派单算法（加入分数后）
    ...
```

### 5.2 数据校验

```python
# 每日定时校验
def daily_consistency_check():
    # 检查 1: 库存与询价匹配统计是否一致
    for inv in Inventory.objects.filter(matched_count__gt=0):
        actual_count = Dispatch.objects.filter(
            seller_id=inv.seller_id,
            created_at__gte=inv.created_at
        ).count()
        if abs(actual_count - inv.matched_count) > 5:
            alert(f'数据不一致：inventory {inv.id}')

    # 检查 2: 卖家偏好是否被正确读取
    for seller in active_sellers:
        if seller.has_inventory_but_no_preference:
            create_default_preference(seller)
```

## 六、回滚预案

### 6.1 单功能回滚（Feature Flag）

```yaml
# 立即关闭功能
features:
  new_session_engine:
    enabled: false  # 一键关闭
```

**生效时间**：< 1 分钟

### 6.2 部分回滚（仅前端）

```typescript
// 客户端：临时下线某个入口
const FEATURES_DISABLED = ['inquiry_entry'];

if (FEATURES_DISABLED.includes('inquiry_entry')) {
  // 隐藏入口
}
```

**生效时间**：发版后

### 6.3 数据回滚（极端情况）

```sql
-- 极端情况：新功能产生坏数据，需删除
-- 注意：必须有 DBA 在场，且事先 review

START TRANSACTION;

-- 备份新表
CREATE TABLE purchase_sessions_backup AS
SELECT * FROM purchase_sessions WHERE created_at > '2026-XX-XX';

-- 检查是否有跨表关联（一定要查清楚！）
SELECT * FROM dispatches WHERE session_id IN (SELECT session_id FROM purchase_sessions_backup);

-- 删除
DELETE FROM purchase_sessions WHERE created_at > '2026-XX-XX';

-- 校验
SELECT COUNT(*) FROM purchase_sessions;

-- 决定 COMMIT 或 ROLLBACK
```

**注意**：数据回滚是最后手段，**优先用 Feature Flag**。

## 七、性能考虑

### 7.1 大表索引

```sql
-- inventory 表已有索引补充
ALTER TABLE inventory
  ADD INDEX idx_dispatch_lookup (product_category, material_grade, delivery_location, accept_inquiry, status);
```

### 7.2 缓存策略

```python
# Redis 缓存热门库存
@cache(ttl=300, key='inventory:hot:{category}:{city}')
def get_hot_inventory(category, city):
    return Inventory.objects.filter(
        product_category=category,
        delivery_location__city=city,
        status='active'
    ).order_by('-matched_count')[:20]
```

### 7.3 异步处理

```
所有"非关键路径"操作改异步：

  - 数据分析

工具：Kafka / RabbitMQ
```

## 十、关键风险

| 风险 | 概率 | 影响 | 对冲 |
|---|---|---|---|
| 数据库锁表 | 低 | 严重 | 用 gh-ost 在线变更 |
| 性能下降 | 中 | 中 | 索引 + 缓存 + 异步 |
| 数据不一致 | 低 | 严重 | 双写 + 校验 |
| Feature Flag 失控 | 低 | 中 | 严格灰度策略 |
| 老用户 API 异常 | 低 | 严重 | 100% 向后兼容 |
