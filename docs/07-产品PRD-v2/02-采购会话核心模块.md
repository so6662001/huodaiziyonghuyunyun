# M2：采购会话核心模块 ⭐

> **本模块是货袋子产品的灵魂**。彻底替代旧 PRD v1 中的"需求-报价"离散原子模型。

## 1. 模块目标

把真实采购的**连续对话流**做成产品的一等公民：
- 30 秒发需求
- 3 秒发变更
- 多卖家并行报价
- AI 自动识变（IM 中说话就能改需求）
- 历史会话永久沉淀

## 2. 用户故事

```
US-2.1（连续对话）
作为一个采购员，我在询价过程中需求经常变（数量、规格、交期），
我希望在平台上修改像在微信里说一句话一样简单，
而不是"重新发一次需求"。

US-2.2（多家并行）
作为一个采购员，我同时和 5 家卖家谈，
我希望一个屏幕能看到所有人的最新报价和状态，
而不是切换 5 个 IM 窗口。

US-2.3（AI 识变）
作为一个采购员，我在聊天中随便说"改成 80 吨"，
平台能自动识别这是数量变更，弹出确认条让我点确认，
而不是让我去"编辑需求"页面。

US-2.4（卖家轻响应）
作为一个卖家，买家变更需求后，
我希望 3 秒内就能选择"维持原价/调整/退出"，
而不是重新走一遍报价流程。
```

## 3. 核心设计

### 3.1 旧模型 vs 新模型

**旧模型（找钢网/初版 PRD v1）**：

```
买家发需求 → 卖家报价 → 买家选 → 联系 → 成交
   ↑__________________|
   每次变更都要重来
```

**新模型（采购会话）**：

```
买家发起"采购会话"
  ↓
系统生成动态需求卡片（DemandCard）
  ↓
N 个卖家通过派单加入会话
  ↓
多方实时对话 + 卡片动态变更 + 报价并行
  ↓
最终成交（一家或多家组合）
```

### 3.2 "采购会话"实体

```
PurchaseSession
  ├─ 1 个 DemandCard（动态需求卡片，可被无限次编辑）
  ├─ N 个 SellerParticipation（参与的卖家）
  ├─ N 条 ConversationStream（每个卖家一条对话流，并行）
  ├─ M 个 Quote（报价，与卡片版本绑定）
  ├─ K 个 Negotiation（议价记录）
  ├─ J 个 ContactRecord（IM/电话/虚拟号记录）
  ├─ 1 个 SessionAggregator（买家聚合看板）
  ├─ 1 个 SessionTimeline（操作时间线，含 AI 识变事件）
  └─ 0/1 个 Deal（成交回填）
```

## 6. 核心接口

```
# 采购会话

GET    /api/v1/purchase-sessions/{id}/aggregated     聚合视图（买家用）
POST   /api/v1/purchase-sessions/{id}/close          关闭会话
POST   /api/v1/purchase-sessions/{id}/clone          克隆会话（创建新会话）

# 动态需求卡片
POST   /api/v1/purchase-sessions/{id}/cards          创建新版本卡片（变更）
GET    /api/v1/purchase-sessions/{id}/cards          查询所有版本
GET    /api/v1/purchase-sessions/{id}/cards/current  当前版本

# 卖家参与
POST   /api/v1/purchase-sessions/{id}/sellers/{seller_id}/accept    卖家接单
POST   /api/v1/purchase-sessions/{id}/sellers/{seller_id}/reject    卖家拒绝
POST   /api/v1/purchase-sessions/{id}/sellers/{seller_id}/withdraw  卖家退出

# 卡片变更响应（卖家端）
POST   /api/v1/cards/{card_id}/response              卖家响应变更
  body: { action: 'maintain_price'|'adjust_price'|'set_tier'|'withdraw',
          new_price?: number, tier_pricing?: object }

# 对话流
GET    /api/v1/purchase-sessions/{id}/streams        所有对话流
GET    /api/v1/streams/{id}/messages                 消息列表
POST   /api/v1/streams/{id}/messages                 发送消息

# AI 识变
POST   /api/v1/ai/detect-intent                      解析意图
  body: { stream_id, message_content }
  return: { intent_type, extracted_fields, confidence }
POST   /api/v1/ai/intents/{intent_id}/confirm        用户确认 AI 识别

# 时间线
GET    /api/v1/purchase-sessions/{id}/events         时间线事件流
```

## 7. 核心业务流程

### 7.1 创建会话主流程

```
1. 买家点击"发需求" → 进入极简发需求页
2. 填写品名/材质/规格/数量/到货地（30 秒内）
3. POST /purchase-sessions
   → 后端创建 Session + 创建 v1 DemandCard
4. 触发 M5 智能匹配
   → 系统按规则推送给 N 个卖家
   → 创建 N 个 SellerParticipation（待接单）
5. 卖家收到推送（App/SMS/企微）
   → 卖家接单 → SellerParticipation 状态 = engaged
6. 卖家报价 → 创建 Quote（关联当前 card_version）
7. 买家在聚合看板看到所有报价
8. 买家选择联系 → 创建 ConversationStream
9. 双方对话 → 创建 Message
```

### 7.2 需求变更流程（核心创新）

```
方式 A：手动编辑
1. 买家点击需求卡片"编辑"
2. 弹出表单，修改字段
3. POST /sessions/{id}/cards（携带变更字段）
4. 后端：
   a. 当前 card.is_current = false
   b. 创建新版本 card.is_current = true
   c. 触发卡片变更通知给所有 engaged 卖家
5. 卖家收到通知
   → "买家把数量从 50 改为 80，您的报价是否调整？"
6. 卖家一键选择：维持/调整/退出
7. 时间线记录该事件

方式 B：AI 识变
1. 买家在 IM 输入"要不改成 80 吨吧"
2. 前端 → POST /ai/detect-intent
3. AI 服务返回：
   { intent_type: 'change_quantity',
     extracted_fields: { quantity_ton: 80 },
     confidence: 0.92 }
4. 前端展示确认条：[是，更新][否，继续聊]
5. 用户点"是" → 转方式 A 流程从步骤 3 开始
```

### 7.3 卡片变更同步策略

```
变更发生时，对每个 engaged 卖家：

字段级响应映射：
  quantity ↑      → 推送：是否设阶梯价？
  quantity ↓      → 推送：维持单价？
  spec 改         → 推送：同价/±N 元/退出
  delivery 变急   → 推送：加急费？
  payment 变长    → 推送：账期溢价？

推送通道：
  App push（即时）
  企微机器人（实时）
  短信（30 秒内未读补发）

响应有效期：60 分钟（默认）
未响应：维持原报价，但标记"未响应变更"
```

### 7.4 变更次数限制

```
免费变更次数：5 次/会话
6-10 次：每次自动给 engaged 卖家 ¥3 积分补偿
>10 次：标记买家为"反复变更"，提示卖家
  + 后续变更进入降权派单
```

## 8. AI 识变设计

### 8.1 LLM 选型

- **首选**：通义千问 / GPT-4 Turbo / 文心一言
- **本地化**：可选部署 Qwen 32B（高频场景降低成本）
- **降级方案**：规则引擎（关键字+正则）

### 8.2 Prompt 工程

```
系统提示：你是一个钢贸采购助手，需要从买家和卖家的对话中识别需求变更意图。

任务：分析以下消息，判断是否包含需求变更，若有则提取变更字段。

当前需求卡片：
  品名：{product}
  材质：{material}
  规格：{spec}
  数量：{quantity} 吨
  到货：{delivery_city}
  交期：{delivery_date}
  账期：{payment}

最新消息：{message}

输出 JSON：
{
  "has_intent": true/false,
  "intent_type": "change_quantity"|"change_spec"|...|null,
  "extracted_fields": {...},
  "confidence": 0.0-1.0,
  "natural_summary": "买家把数量改为 80 吨"
}

特别注意：
- 钢贸行话："螺18"=螺纹 ¢18mm；"30T"=30 吨；"H50T"=工字钢..
- 模糊表达："要不"、"能不能"应识别为询问而非确认
- 数量范围："50-80 吨"应识别为模糊询价
```

### 8.3 准确率与回退

| 置信度 | 处置 |
|---|---|
| ≥ 0.85 | 直接展示确认条 |
| 0.6-0.85 | 展示确认条 + 高亮提示"AI 不确定" |
| < 0.6 | 不打扰用户，仅后台记录 |

错误时用户可"撤销 AI 识别"（48 小时内）。

### 8.4 数据沉淀

```
每次 AI 识变后：
  - 记录原始消息
  - 记录 LLM 输出
  - 记录用户是否确认
  - 用户拒绝识别 → 标记为负样本
  - 月度回训 → 提升准确率

成本控制：
  - 单次 LLM 调用 < ¥0.01
  - 月预算上限 < ¥5000（M3 时）
```

## 9. 状态机

### 9.1 PurchaseSession

```
created → active → matching → quoting → negotiating → deal
   ↓        ↓         ↓          ↓           ↓
 cancelled cancelled cancelled cancelled  closed
                       ↓
                    expired（72h 无活动）
```

### 9.2 DemandCard

```
draft（极少出现）→ active
                    ↓
                  superseded（被新版本替代）
                    ↓
                  archived（会话关闭后归档）
```

### 9.3 SellerParticipation

```
invited → engaged → quoted ─→ won
              ↓        ↓        ↓
          rejected  withdrew  lost
                            ↓
                       expired
```

## 12. 异常处理

| 场景 | 处理 |
|---|---|
| 24h 内 0 报价 | 平台运营介入扩匹配 + 通知买家"系统正在为您扩大范围" |
| 卖家变更未响应（>1h） | 维持原报价，标记"未响应"，影响后续派单权重 |
| AI 识变错误（用户撤销） | 撤销卡片变更 + 记录负样本 |
| 变更次数 > 10 | 提示买家"反复变更可能影响卖家积极性" |
| 会话超时（72h 无活动） | 自动归档，可手动复活 |
| 卡片版本冲突（并发编辑） | 后写入获胜，给前者发"变更被覆盖"通知 |
